                            Workload Identity Federation, CI service accounts, budgets

## One-time bootstrap

You need Terraform ≥ 1.9 and `gcloud` signed in as someone with, on the
`solidrocksolutions.co` organization: **Project Creator**, **Billing Account User** and
**Billing Account Costs Manager** on billing account `017CE5-553A7B-1BF9F5`, and permission to
grant org-level IAM (for `sa-plan`'s Organization Viewer).

1. Confirm the region (section 24.2). Default `us-south1`. Cloud Run (incl. worker pools),
   Cloud SQL Enterprise and KMS are available there. **Check that your chosen Gemini model is
   offered in `us-south1` before M2**; if not, set `region = "us-central1"` now, before any data
   exists — all resources must be in one region.
2. `gcloud auth application-default login`
3. `GITHUB_REPOSITORY=owner/repo ./infra/bootstrap.sh`
   - applies `shared` with local state, moves the state into the new bucket,
   - applies `envs/staging` (Cloud Run starts with Google's placeholder image),
   - prints the GitHub repository variables to set.
4. In GitHub → Settings → Secrets and variables → Actions → **Variables**, set the printed
   values (`GCP_WIF_PROVIDER`, `GCP_DEPLOYER_SA`, `GCP_PLAN_SA`, `GCP_REGION`,
   `GCP_STAGING_PROJECT`, `ARTIFACT_REGISTRY`, `TFSTATE_BUCKET`, `STAGING_URL`). There are no
   secrets to set: authentication is keyless.
5. Create a GitHub environment named `staging` (optionally with protection rules).
6. Merge to `main` (or run *Deploy staging* manually). The pipeline builds, scans, migrates,
   deploys and smoke-tests.
7. Run `terraform fmt -recursive infra` once and commit (the files were written without a
   Terraform binary; CI only warns on formatting).

## Day to day

- **Pull requests** touching `infra/**`: `terraform validate` always; `terraform plan`
  (read-only `sa-plan`, `-refresh=false`) once the variables exist.
- **Applying** Terraform changes is manual in M0 (an eng admin runs `terraform apply` in the
  changed root). Production applies will require approval (24.7).
- **Images**: Terraform ignores the container image; CI owns it. Everything else about the
  services (env vars, secrets, scaling, identity, networking) is Terraform's.

## Things to know

- **No load balancer yet.** Staging is served from the `web` run.app URL with
  `invoker_iam_disabled = true` (avoids an `allUsers` grant that domain-restricted-sharing org
  policies block). The external LB, managed certificate and Cloud Armor arrive in M8.
- **Email is off in staging** until a Postmark server exists: magic links are hidden and the
  inviting Admin sees the invite link on screen. To turn email on: add a version to the
  `POSTMARK_SERVER_TOKEN` secret, mount it on `web` and `worker`, and set `magic_link_enabled`.
- **Secrets in state.** Database passwords and `AUTH_SECRET` are generated by Terraform, so they
  are in the state bucket (access: eng admins, `sa-plan` read). Tighten before production (M8).
- **Smoke test** signs up a throwaway firm on every deploy (staging holds synthetic data only).
- **Staging monthly cost** is dominated by Cloud SQL (`db-custom-1-3840`) and `clamav` (min 1
  instance, CPU always allocated). Budget alerts at 50/90/100 % of `budget_staging_usd`.
